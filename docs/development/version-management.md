## 1 版本规则

应用采用三段数字：`主版本.功能版本.修复版本`。

| 变更 | 操作 | 示例 |
| --- | --- | --- |
| bug 修复 | 第三位加一，前两位保持 | 0.1.0 → 0.1.1 |
| 大功能更新 | 第二位加一，第三位归零 | 0.1.3 → 0.2.0 |
| 主版本调整 | 仅项目负责人手动指定，AI 不自主调整 | 用户指定 1.0.0 |

一个完成并验证的逻辑交付递增一次，过程中的多次编辑、测试或随后补充验收记录的文档提交不重复递增。混合大功能与 bug 修复按一次功能版本更新。纯文档和不含 bug 修复或大功能的日常维护不强制递增；其他边界变更明确记录分类，不自动推断为大版本。

新规则从既有 `0.1.0` 基线开始执行，不追溯给旧功能和候选包重新编号。版本标记只表明代码阶段，不表示已正式发布，不自动打包或覆盖安装。

## 2 统一来源与同步字段

`package.json.version` 是唯一人工维护来源。工具将其同步到 `src-tauri/tauri.conf.json.version`、`src-tauri/Cargo.toml` 的本项目 package.version，以及 Cargo.lock 中本项目包的版本；不修改第三方依赖版本。界面通过 app_info.version 展示编译时的 Cargo 包版本，取消固定版本文字。

应用版本与 SQLite schema、复习策略、同步协议和文档自身修订号分别维护；应用升级不自动修改这些编号。旧安装包和源码材料保持其原始基线与摘要，不能拿当前源代码号代替旧包版本。

## 3 操作入口

在项目目录执行：

```powershell
pnpm version:patch --message "修复候选词列表显示错误"
pnpm version:minor --message "增加新的学习功能"
pnpm version:check
```

前两条要求提供单行变更说明，同步四个版本字段，并向根目录 CHANGELOG.md 追加新版本记录。工具按所在脚本定位项目，支持从其他工作目录通过绝对路径调用。Windows 安装版本每段限定为 0–65535，拒绝不规范格式与降级设置。

人工修改 package.json 后，可用 `pnpm version:sync` 同步其余字段；此操作不递增版本或新增变更记录。主版本由负责人手动设置，例如：

```powershell
pnpm version:set 1.0.0 --message "负责人决定进入 1.0"
```

此命令供用户手动执行，不能由 AI 根据工作量或自身判断自主调用。没有自动 major 命令。工具不创建提交、分支、标签或 GitHub 发布。

## 4 开发与发布流程

1. 完成功能或 bug 修复，并执行与影响相称的本地验证。
2. 按变更类型递增一次版本，记录具体变更，检查版本一致性，再提交与推送必要文件。
3. 前端 dev/build 及发行打包、源码导出入口会检查版本一致性，不一致时停止。
4. 用户需要版本发布时，手动执行 `pnpm desktop:package`；产物目录及名称使用当前统一版本。
5. 按发布要求验证安装与源码材料，用户明确要求发布标签时再创建 `v主版本.功能版本.修复版本`。重复构建同一版本不另行递增。

## 5 本轮验证

`pnpm test:version` 在独立临时目录验证连续修复递增、功能版本归零、主版本保持与手动设置、降级/不规范/缺少说明的拒绝、四字段同步、第三方依赖保持、变更日志以及一致性检查/修复。失败操作在写入前被拒绝，测试不修改本项目实际版本或词库。测试完成核对临时目录的绝对位置后清理。

源码导出中的依赖版本使用独立变量，避免覆盖项目版本导致源码包名称错误。本次修复以首个受新规则管理的 `0.1.1` 记录；只执行本地检查和构建，不生成发行包。
