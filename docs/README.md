本项目采用需求、设计、实现、验证和交付相互追溯的文档流程。每类文档承担明确职责，已确认决策、设计提案和实现结果分别标注，避免把讨论中的设想直接写成已承诺或已完成的能力。

## 1 文档分类与职责

| 类型 | 当前或后续位置 | 必须包含 | 职责边界 |
| --- | --- | --- | --- |
| 产品需求 PRD | [requirements/PRD.md](requirements/PRD.md) | 背景、目标、范围、流程、需求编号、业务规则、验收标准、待确认项 | 描述需要满足的行为和结果；具体框架、代码结构和数据库实现属于设计文档 |
| 需求审查 | [requirements/review.md](requirements/review.md) | 审查对象、方法、结论、开放事项与后续成果 | 文档层核对不代表功能验收或新增范围已确认 |
| 架构设计 | [design/architecture.md](design/architecture.md) | 需求依据、系统边界、技术决策、模块与依赖、数据流、集成约束、风险与追溯 | 解释如何组织系统；引用需求，不重新定义产品范围 |
| 详细设计 | [数据模型](design/data-model.md)、[应用流程](design/application-flows.md)、[接口契约](design/interfaces.md) | 接口契约、数据结构、状态转换、异常处理、对应需求编号 | 补足实现所需细节；简单模块可在架构文档内完成，避免重复文件 |
| 验证与验收 | [testing/test-plan.md](testing/test-plan.md)；实际记录随验证放入 `testing/` | 计划包含环境、需求、输入、步骤和预期；记录补充实际结果与证据 | 测试计划在设计阶段建立，执行记录在实际验证后形成 |
| 原型验证记录 | [testing/prototype-results.md](testing/prototype-results.md) | 实际环境、工具、素材标识、结果和未覆盖项 | 只证明具体原型边界，不代替完整功能验收 |
| 开发计划 | [planning/development-plan.md](planning/development-plan.md) | 阶段、依赖、交付、需求测试关联与完成依据 | 安排实施顺序，不复制技术选型或编造进度 |
| 交付与使用 | 可运行版本形成后按需放入 `release/` 或更新根 README | 版本、安装运行方法、依赖资源、变更与已知限制 | 只描述已交付行为，不提前编造安装命令和功能状态 |

当前已建立需求、审查、架构、详细设计、测试计划和开发计划。原型记录、测试结果及安装交付说明随对应工作形成，不创建没有内容的占位文件。

### 1.1 阅读与维护顺序

1. PRD 定义要满足的行为；需求审查记录其完整性与开放事项。
2. 架构定义系统分工；数据、流程与接口设计补足可实施的契约。
3. 测试计划将需求转为可执行场景；开发计划按依赖安排增量。
4. 实施时更新设计与真实验证记录；可运行版本形成后编写交付说明。

上述顺序允许按功能增量反复执行，文档状态与工作进展分别维护。

## 2 文档结构

需求、设计和验证等正式文档应包含明确标题、文档编号、版本、更新日期、状态、正文和修订记录。正文按文档职责组织，使用分节、表格和必要的流程图。根 README 作为项目入口、AGENTS.md 作为开发约束，可采用与其职责相符的简明结构。

需求应当可理解、可验证，并说明触发条件、系统行为和验收结果。框架名称、库版本、服务地址、协议与数据库表结构应进入架构或详细设计；运行平台、离线能力等产品约束可以进入 PRD。

跨文档引用使用仓库相对路径。相同事实应有唯一维护位置，其他文档使用引用，减少多个文件各自维护一套需求或技术栈。

## 3 状态与基线

| 状态 | 含义 |
| --- | --- |
| 初版待评审 | 文档已形成，等待核对完整性与准确性 |
| 已确认 | 内容得到项目负责人确认，作为后续实施基线 |
| 修订中 | 正在调整已确认内容，保留原决策和变更说明 |
| 已废止 | 已被新的内容取代，保留历史与替代引用 |

文档状态与功能实现状态分开管理。文档发布到 GitHub、代码编译通过或测试计划写完，都不能自动表示功能已经验收。

已经在讨论中确认的范围和技术栈，可以在初版文档中标为已确认事项；尚未确认的算法、引擎、协议和参数应进入待决策表。例句等演示内容属于说明，不是新增需求。

## 4 工作流程

1. **需求整理**：将用户意图转为范围、业务规则、需求编号和验收标准；把不确定事项列为待确认项。
2. **需求评审**：核对需求是否遗漏、互相矛盾、超出授权，确认实施基线。
3. **架构与详细设计**：引用需求编号，确定模块和接口；必要时用小规模原型验证技术风险，并记录结果。
4. **实现**：按已确认需求和设计交付代码，日常实现选择在授权范围内自主处理。
5. **验证与验收**：执行需求对应场景，记录实际结果、失败项和环境边界。
6. **交付**：同步文档与实际行为，提交并推送必要文件，给出版本和可使用的交付物。

此流程按功能增量执行。已获用户授权的工作不因文档流程增加重复确认；影响产品范围、关键行为或已确认技术决策的新变更，需要明确其依据与确认状态。

## 5 需求追溯与变更

- 功能需求采用 `FR-01` 等编号，非功能需求采用 `NFR-01` 等编号；编号一经建立，不因重新排序而复用。
- 架构模块采用 `ARC-01` 等编号，架构决策采用 `DEC-01` 等编号。
- 需求审查采用 `REV-01`，本地命令采用 `CMD-01`，测试场景采用 `TC-01`，实施阶段采用 `M-01` 等稳定编号。
- 架构文档维护需求与负责模块的对应关系。实现后，验证记录再关联同一需求编号。
- 变更记录说明变更内容、来源、影响文档、确认状态和验证影响。小变更可记录在文档修订表及 Git 提交中，无需另建审批系统。
- 需求变更应先更新或同时更新对应设计与验收；设计优化不能自行扩大需求范围。
- 待确认事项关闭时，应把结果写回正文与追溯表，避免正文与待确认项互相冲突。

## 6 文档检查与发布

提交前检查以下事项：

- 产品名称统一，日期、版本和状态准确。
- PRD 与设计职责分离，已确认项与提案清楚区分。
- 0.1 需求均有验收标准，架构模块能追溯到需求。
- 内部链接有效，需求编号唯一，图表与正文一致。
- 未写入真实凭据、个人词库、影视媒体或与公开维护无关的个人信息。
- README 的功能状态与实际交付一致。

通过检查后按当前分支提交并推送。后续代码变更按影响执行适当测试，公开仓库的创建不代表软件实现或部署已经完成。

## 7 规范参考

本规范参考 [ISO/IEC/IEEE 29148:2018](https://www.iso.org/standard/72089.html) 的需求工程范围和 [ISO/IEC/IEEE 42010:2022](https://www.iso.org/standard/74393.html) 的架构描述职责，按个人桌面项目规模裁剪文档与流程。这里采用项目文档规范，不声明完整符合上述标准或通过认证。
