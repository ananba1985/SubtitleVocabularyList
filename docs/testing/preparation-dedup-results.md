## 1 问题与修改

0.6.1 的列表按候选词去重，但后台按“词语＋每句完整对白”准备解释。当前 24 集有 21,273 个分集候选，跨集只有 6,140 个不同词／短语，却展开为 73,190 个组合。合批减少了 HTTP 次数，但没有消除组合膨胀。

0.6.2 的通用释义按规范化词键保存在 explanations 的空 context 项中，跨集复用；整句译文保存到独立 sentence_translations，每个完整原句只准备一次。008 迁移从原有语境解释复用已保存译文，旧语境释义不删、不当作通用词义。已掌握偏好保持，未掌握候选关联的句子参与准备；特殊语境解释仍由用户明确请求，不默认全量展开。

后台保留并发、合批、取消、重试和逐项保存。通用词义与句子译文分批请求，任务分别显示两类计数；旧历史保留其原统计口径。读取优先已有语境解释，其次通用词义，已保存句子译文可在词义未完成时先显示；通用结果标明“通用释义”。候选列表只等待词义，选中详情才继续刷新未完成译文，页面读取不触发模型调用。

## 4 批量模型请求固定超时（0.26.8）

2026-10-24，FR-08／NFR-03。用户安装版 0.26.6 的任务停在 310／736，4 集，10 项在途，截图显示第 38 次自动重试。通过 SQLite 只读连接取得同一任务时已为第 39 次：已生成 297 项，通用词义 3／19、句子译文 307／717，配置为每次 10 项、并发 1。没有修改或暂停该任务。

实际模型 `/health` 返回 200／ok，`/slots` 显示一个任务正在生成，`max_tokens=1200`、非流式；这与 `explain_many` 的 10 项词义预算 `200 + 10 × 100` 一致。模型日志中相同请求连续重新启动，生成速度约 8.4～8.6 token／秒；例如 task 27560 在相对时标 `818.33.755` 启动，`819.33.838` 收到客户端 cancel，最后记录仅生成 405 token。源码 `model_content` 固定 60 秒总超时，`provider_error` 将其标为可重试，worker 等待后原样再发这批，所以相同请求重复消耗生成时间，未完成整个 JSON 就被取消。

此次失败发生在接收完整模型答复之前，不是这批结果被字段校验拒绝。另列的 13 项未完成包含无有效中文词义、无有效中文译文两类保存校验原因，缺少其原始模型答复，本轮未将其解释为同一超时原因，也未编造词义或修改 OCR 原文。

修复及等待预算见[架构 ARC-05](../design/architecture.md)。后台输出预算 1200 token 时上限为 180 秒；共用现有可取消异步实现，连接超时仍为 5 秒，题库独立期限保持。超时消息包含实际等待上限，不清空旧解释、译文或学习记录。

最小正常验证：

```powershell
cargo test --locked --manifest-path src-tauri/Cargo.toml --features desktop --lib batch_explanations::tests::ten_item_batch_uses_generation_budget_and_saves_complete_results -- --exact
```

**1 passed、0 failed**，执行 0.12 秒，不含编译。直接核对生产期限函数对 1200 token 返回 180 秒；隔离 HTTP 模型替身收到 10 个目标、1200-token 输出预算及原 vocabulary_explanation schema，完整返回后，生产 `explain_many` 和任务流程成功，10 项中文解释全部持久化，个人词条为空。仅运行该正常用例，未制造超过 60 秒的延迟或追加故障／取消／压力场景。

最初使用无桌面 feature 的 lib 单测命令在既有 `assessment_tests` 对 `sync_test_fixture` 的条件编译处失败；改用桌面 feature 后执行同一用例通过，没有修改无关测试条件。正式 Data 的访问全为只读，模型仅健康／槽位读取及既有日志取证，没有追加真实生成请求或改动启动参数。私有诊断、模型日志摘录及正常测试记录保留在 `.local/preparation-timeout-0.26.8/`。本轮没有打包、安装或重启用户客户端；安装版原任务不会自动使用源码修复，真实模型在修复版的完整生成和 13 项内容问题仍需后续分别核对。
